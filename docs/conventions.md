# 개발 규칙

- 상태: 초안 (2026-11-26). 팀의 확인을 기다림
- 대상: dev_tools를 만드는 사람과 그 사람이 쓰는 AI 개발툴

## 1. 일하는 순서

1. 할 일을 고른다. 2단계 전에는 `docs/requirements.md`에서, 2단계 뒤에는 dev_tools의 빈 곳 찾기에서 고른다.
2. 맡았다고 알린다. 2단계 전에는 팀 대화 수단에 요구사항 ID를 적고, 2단계 뒤에는 dev_tools에서 맡는다.
3. 요구사항마다 브랜치와 작업 공간(git worktree)을 따로 만든다.
4. 구현하고, 요구사항 ID를 적은 테스트를 함께 쓴다.
5. 테스트가 통과하면 PR을 올리고 다른 팀원 한 명의 확인을 받는다.
6. 합친 뒤 작업 공간을 지운다.

## 2. 요구사항과 스펙

- 요구사항 ID는 `REQ-영역-번호` 형식이다(예: `REQ-TSK-003`). 영역은 `docs/requirements.md`의 표를 따른다.
- 한 번 붙인 ID는 바꾸지 않고, 없앤 요구사항의 ID를 다시 쓰지 않는다.
- 요구사항은 하나의 검사할 수 있는 문장으로 쓴다. "~한다", "~할 수 있다"로 끝내고, 두 가지를 한 문장에 넣지 않는다.
- 요구사항을 더하거나 고치는 일도 PR로 한다.

## 3. Git

| 항목 | 규칙 | 예 |
|---|---|---|
| 기본 브랜치 | `main`. 직접 푸시하지 않는다 | |
| 작업 브랜치 | `req/<요구사항 ID>-<짧은 설명>` | `req/REQ-TSK-003-atomic-claim` |
| 요구사항이 없는 작업 | `chore/<짧은 설명>`, `docs/<짧은 설명>` | `docs/tech-design` |
| 커밋 제목 | 영어 명령형. 관련 요구사항 ID를 끝에 괄호로 | `Reject concurrent claims (REQ-TSK-003)` |
| PR | 요구사항 하나에 PR 하나를 기본으로 | |
| 합치기 | 다른 팀원 한 명의 확인과 CI 통과 뒤 | |

브랜치 이름에 요구사항 ID를 넣는 것은 dev_tools가 세션과 맡은 일을 잇는 데 쓰기 때문이다(`docs/tech_design.md` 6장).

## 4. 테스트

- 요구사항을 구현하면 그 요구사항을 검증하는 테스트를 적어도 하나 쓴다.
- 테스트 이름의 맨 앞에 요구사항 ID를 적는다.

```ts
test("REQ-TSK-003: 두 사람이 동시에 맡으면 한 사람만 성공한다", async () => {
  // ...
});
```

- 한 테스트가 여러 요구사항을 검증하면 ID를 쉼표로 나열한다.
- 실제 도구에서 받은 이벤트 표본은 `webapp/packages/adapters/<도구>/fixtures/`에 도구 버전과 함께 둔다.
- AI 모델을 부르는 테스트는 녹화한 응답을 재생한다. 실제 호출은 평가 측정 때만 한다.

## 5. 코드

- 코드, 식별자, 주석은 영어로 쓴다. 문서와 화면의 글은 한국어로 쓴다.
- 화면의 말은 `docs/ui_concept.html` 1장의 쉬운 말을 따른다. 화면 글귀는 한 파일에 모아 둔다.
- 상태 계산 규칙은 `webapp/packages/shared`에만 둔다. 서버와 화면에서 따로 다시 만들지 않는다.
- 어댑터는 서버와 화면의 코드를 참조하지 않는다.
- 새 의존성을 더할 때는 라이선스를 확인한다. AGPL, 상용 제한, 비상용 라이선스는 쓰지 않는다(D-20).

## 6. AI 개발툴 사용

- 작업을 시작하기 전에 맡은 요구사항의 ID와 원문을 AI 개발툴에 알려 준다.
- AI 개발툴이 스스로 일을 골라 맡게 하지 않는다. 맡기는 사람이 결정한다.
- AI 개발툴이 "다 됐다"고 해도 테스트 결과로 확인한다.
- 맡은 요구사항의 범위를 넘는 변경이 필요해 보이면 멈추고 팀에 알린다. 다른 사람이 맡은 파일일 수 있다.
- 비밀 값(토큰, 열쇠)을 프롬프트나 코드에 넣지 않는다.
- AI 개발툴용 지침은 `CLAUDE.md`와 `AGENTS.md`에 두고 두 파일의 내용을 같게 유지한다.

## 7. 문서

| 문서 | 고치는 때 |
|---|---|
| `dev_tools_definition.md` | 제품의 범위나 원칙이 바뀔 때 |
| `docs/requirements.md` | 요구사항을 더하거나 고칠 때 |
| `docs/decisions.md` | 무엇이든 결정했을 때. 기존 행은 지우지 않는다 |
| `docs/tech_design.md` | 구조, 데이터 모델, API가 바뀔 때. 코드와 같은 PR에서. 18장의 구현 현황도 함께 |
| `development_plan.md` | 단계의 범위나 순서가 바뀔 때. 일이 끝나면 진행 현황 표를 고침 |
| `CLAUDE.md`, `AGENTS.md` | 빌드·테스트 명령이나 구조가 바뀔 때 |

- 확인하지 못한 내용은 **[미확인]** 으로 표시한다.
- 추정한 숫자에는 추정이라고 적는다.

## 8. 완료의 뜻

요구사항 하나가 끝났다는 것은 다음이 모두 참이라는 뜻이다.

1. 요구사항 ID가 적힌 테스트가 있고 통과한다.
2. CI가 통과한다.
3. 다른 팀원 한 명이 확인했다.
4. 구조나 API가 바뀌었다면 문서가 함께 고쳐졌다.
